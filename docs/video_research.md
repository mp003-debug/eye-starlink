# 本地视频预研

2026-10-31。结论：已有依赖可以解码低分辨率本地视频，建议进入受限的第一版实现。先用320×180、目标8fps、30–60秒短片；480×270保留为后续候选。**本轮未实现或部署视频播放器，未开启摄像头、显示DMA或AUX播放。** 当前板端仍是相册/输入UI v8验证包。

## 本轮实测

板卡PYNQ-Z2/armv7l、两核、OpenCV4.5.4，FFmpeg后端可用（avcodec58.134.100、avformat58.76.100、swscale5.9.100）；独立ffmpeg/ffprobe命令不存在，本轮未安装依赖。开发机用已有FFmpeg7.1生成6秒、12fps、72帧移动测试图，每种尺寸分别转RGB565原始帧、MJPEG/AVI和H.264 baseline/MP4，无音轨、无B帧。没有下载影视内容。

| 尺寸 | 格式 | 6秒样本大小 | 板端单帧读入/解码P95 |
| --- | --- | ---: | ---: |
| 320×180 | raw | 8.294 MB | 0.444 ms |
| 320×180 | mjpeg | 0.649 MB | 5.274 ms |
| 320×180 | h264 | 0.151 MB | 2.878 ms |
| 480×270 | raw | 18.662 MB | 0.939 ms |
| 480×270 | mjpeg | 0.923 MB | 10.202 ms |
| 480×270 | h264 | 0.266 MB | 5.779 ms |

解码列不包含RGB565转换、缩放、UI、相机等待和DMA；不能把倒数当作实际播放帧率。此前哈希读取会使素材进入页缓存，因此这些是缓存文件路径与CPU测量，不是冷SD吞吐。

又在同一进程加入当前冻结模型对5张已保存中央参考图的特征/分类计算及基础UI绘制。每轮72帧，未发送任何眼控动作，也未利用重复图建立新的校准或准确率证据。初始480×270 H.264整体CPU循环P95为109.826ms、最大152.330ms；这已经表明不能直接把解码塞进当前眼控循环并承诺12fps。

试验发现NumPy逐像素索引缩放开销明显。换用预先计算的整数映射与OpenCV最近邻remap，保持RGB565字值和选定采样位置一致：320档含UI合成中位29.193→20.755ms，480档28.815→20.834ms；优化后含眼图重放的完整CPU循环P95分别86.083/90.960ms，最大94.988/106.008ms。它们仍不含实时采集/DMA/声音，且只加载基础UI，没有完整输入字库与缓存。直接resize在480档与整数采样参考存在边界取整差异，故采用固定映射并逐像素检查，未把打包色值做线性插值。

优化两轮RSS分别170248/171072KiB，只是研究进程的采样，不能代替完整播放器或解码子进程的总内存测量。14组板端基准全部得到72帧并正确结束，共1008帧（包含相同素材的重复处理）；开发机对应检查通过。42张保留RGB565样本已审阅，48传回文件SHA256核对。没有新增长测或真人视频验收。

## 拟采用的实现

1. 开发机将用户选定且允许使用的视频预转换为固定尺寸、固定帧率H.264 baseline MP4，短GOP、无B帧；有声内容另转PCM16/mono/16kHz WAV。板端继续完全离线运行，新增显式启用参数，默认关闭。先限制每段60秒、有限条数与导入后总容量，不导入未经转换的任意高码率文件。
2. 解码在可终止的独立工作进程中进行，最多保留两帧，按会话编号丢弃旧结果；眼控循环只取已准备好的帧，不阻塞等待解码。缺帧可跳过迟到画面，连续超时则停止并提示。后台解码与两个眼特征线程争用CPU/内存的情况仍需集成实测。
3. 有声视频以PL实际消费样本数为时钟，按 `floor(consumed_samples × fps / 16000)` 选画面；无声视频用暂停可冻结的单调时钟。暂停同时冻结音画；恢复从保存位置重新对齐；帮助立即停视频声音、播放原帮助并保持暂停，返回/BTN2/退出清空队列并停止双方。第一版不做自由拖动进度、倍速或在线流媒体。
4. 观看页将画面放在上部352×198区域，下方保留原位置的大“需要帮助”和“播放控制”，上方两区禁用，减少观看内容时误触。控制页再提供播放/暂停、选片、返回。文字中心继续对齐原注视锚点，不靠缩小按钮腾空间；真实注视动态画面是否会误触仍需用户测试。

## 存储与后续检查

本组480×270/12fps原始RGB565固定需要186.624MB/分钟；同组H.264测试片外推约2.659MB/分钟，但真实片大小取决于内容与编码设置。16kHz单声道PCM16额外约1.92MB/分钟。原始帧适合作为测量对照，不作为默认曲库式存储方案。最终容量以转换后的文件实数为准，板上本轮记录约17.91GB空闲，无镜像/分区修改。

下一步先实现导入、清单校验、解码隔离和音画状态控制，完成离线检查；再做短时静音实际显示，随后测有声同步及帮助/返回/BTN2抢占，最后开展真实眼控观看与混合负载观察。采集间隔、眼控响应、最大暂停延迟、音画偏差、CPU/PSS/RSS和清理情况需共同验收，不能沿用旧音乐20分钟结论。不放宽原150ms输入年龄、1秒停留或300ms有效移开。

116个已安装运行文件与49个选定保底文件核对不变；个人模型/分类器/位流/HWH/音频18项未改，收藏“你”和音乐100%保留。标准服务状态未改，硬件空闲、SSH已关闭。无线与02/03/04仍暂停。当前完整可运行包仍为daily_tools阶段的verified包，本研究包不作为播放器发布包。

用户本轮明确反馈分组输入效率不理想、对眼控患者不够友好，并要求原计划推进完成后再改。后续优先评估常用词/短句、减少分组与返回层级、候选排序和连续输入；以完成目标短句的选择次数、用时与疲劳反馈衡量，不直接用本次带讲解/重新定位的总时长计算打字速度。本轮不修改现有输入流程。
